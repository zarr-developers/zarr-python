The `cast_value` codec now checks that the array's fill value survives a round trip through the codec, as the [`cast_value` spec](https://github.com/zarr-developers/zarr-extensions/tree/main/codecs/cast_value#data_type) requires. Previously `out_of_range="clamp"` or `"wrap"`, or rounding, could encode the fill value to something that decodes to a different value, so the unwritten part of a partly written chunk read back as that value instead of the fill value. For example, a `float32` array with fill value `1000.0` and an `int8` target with clamping read `127.0` there. Creating such an array now raises a `ValueError` that names the fill value, both data types, and the value it decodes to. Opening an array already stored with such a fill value still works: it keeps its fill value, and a warning says what its partly written chunks hold and how to fix it. The check runs once when metadata is created or read, not for every chunk, and the codecs inside a shard are checked with the array's fill value rather than the data type's default scalar, so a shard's codec chain is no longer refused for a fill value it would never be asked to encode.
