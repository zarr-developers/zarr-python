Array creation is now O(1) in the number of chunks per dimension. Chunk
normalization returns a `ChunkGrid` whose uniform dimensions are stored as a
size + extent pair (`FixedDimension`) instead of being expanded to one entry
per chunk, so creating arrays like
`zarr.create_array(store, shape=(2**62,), chunks=(1,), dtype='int32')` succeeds
instantly instead of raising `ValueError` or allocating gigabytes of memory.
The intermediate `ChunksTuple` representation was removed in the process, and
`ChunksLike` now admits per-dimension specs that mix a bare int (uniform chunk
size) with explicit edge-length sequences, matching what the normalizer and
the rectilinear grid spec already accepted.

Coordinate selections (including `vindex` masks) and orthogonal selections with
integer or boolean arrays no longer allocate memory proportional to the total number of
chunks in the array, nor loop over every chunk in Python. Previously a selection of a few
points on an array with billions of chunks could raise `MemoryError`, and a boolean array
along a finely chunked axis paid a Python-level pass per chunk; indexing cost now scales
with the number of selected points (plus, for a boolean array, the length of the array
itself). The internal indexers now store per-occupied-chunk run offsets
(`chunk_run_ends`); the dense `chunk_nitems` / `chunk_nitems_cumsum` attributes of
`CoordinateIndexer`, `IntArrayDimIndexer` and `BoolArrayDimIndexer` are deprecated but
keep their original semantics — note that reading them rebuilds the dense per-chunk array
they used to hold, so on a huge array they still cost what they always did.

`zarr.core.common.ceildiv` now divides integers exactly instead of through a float, so
chunk counts of dimensions longer than `2**53` are correct; previously
`ceildiv(2**62 - 1, 1)` rounded to `2**62`, which put sparse selections near the end of
such a dimension out of bounds.
