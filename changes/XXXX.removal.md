Metadata built in code is strict about chunk edge lengths: `ArrayV2Metadata(chunks=...)`, `RegularChunkGridMetadata`, `RectilinearChunkGridMetadata` and `ShardingCodec(chunk_shape=...)` take them as Python `int`s of at least 1. A chunk size of 0 now raises a `ValueError`, as in `ArrayV2Metadata(chunks=(0,))` for an empty array (use a chunk size of 1; stored metadata with a chunk size of 0 is still read, by `from_dict`, as one chunk spanning the axis). A `bool` or a NumPy integer, including a scalar `chunks=np.int64(5)`, raises a `TypeError`, as a float already did, and as does a chunk shape that is not a list or tuple. Stored metadata is unaffected: a stored rectilinear chunk grid with float edges (`[[4.0, 2]]`) is still read, with a warning. The array creation functions still accept NumPy integers in `chunks=` and `shards=`.

A boolean anywhere in a chunk specification given to the array creation functions (`chunks=True`, `np.True_`, a boolean array, `chunks=(True, 5)`, or a boolean edge in a list) raises one `TypeError`, instead of being read as a chunk size of 1 or raising a different error for each spelling; `chunks=True` and `chunks=None` raised a `ValueError` before. The legacy `zarr.create(..., zarr_format=2)` no longer reads a falsy `chunks` as not given: `chunks=0` and `chunks=[]` raise a `ValueError`, and `chunks=False` means one chunk spanning the array, as it does for Zarr format 3, instead of automatic chunking.

`zarr.testing.strategies.chunks_param_from_rectilinear` is removed; nothing in zarr used it after `arrays()` began drawing its `chunks=` argument from `rectilinear_chunks`. `rectilinear_chunks` now returns `list[int | list[int]]` instead of `list[list[int]]`: a dimension may be a bare int step, which can exceed the extent, so code that treats every dimension as a list of edges (`len(dim)`, `sum(dim)`) must handle ints. It also requires `shape` to have at least one dimension.
