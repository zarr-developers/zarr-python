**Breaking:** metadata is read against definitions in a scope, and every
model is the pair of its document and the scope it was read in. A field
(a v3 data type, chunk grid, chunk key encoding, codec or storage
transformer; a v2 dtype or numcodecs codec) is `AcceptedField` by the definition
in scope that claims its name, `UnclaimedField` when nothing does, or
`RefusedField` with every problem; `read_array_metadata_v3`,
`read_group_metadata_v3`, `read_node_metadata_v3` and
`read_array_metadata_v2` read a document once and return everything the
read found, the model among it. A model is built from a document in a
scope (`CORE_AND_EXTENSIONS` or `CORE_V2` by default) and is never
invalid; two models are equal when their documents mean the same;
`update` reads new members, given as JSON, in the model's own scope,
`with_context` and `refined_in` read the document in another, and
`refines` orders models by information. A scope is of one Zarr format, `ZarrV2Context` or `ZarrV3Context`
(`CORE_V2` and the v2 kinds are in `zarr_metadata.v2.definition`, the v3
kinds and scopes in `zarr_metadata.v3.definition`, and what both share in
`zarr_metadata.definition`), and a
reader given a scope of the other format raises `TypeError`; scopes
compare, join and report disagreements, a group's consolidated metadata accepts node models,
number types carry their bounds and problems carry `input` and `ctx`,
JSON Schemas are exported for a TypedDict, a field and a `zarr.json`,
and `read_repaired_node_metadata_v3` and
`read_repaired_consolidated_metadata_v2` undo known writer bugs below
the strict model. Gone: the dataclass models, the model `...Partial` TypedDicts (now
`...Update`), `ZarrV3NamedConfig` and `ZarrV3MetadataField` (from `zarr_metadata`,
`zarr_metadata.model` and `zarr_metadata.pydantic`, with no pydantic
replacement); the other
removals and the names that moved are listed under Deprecations and
Removals. Refused where accepted before: extension names outside `^[a-z][a-z0-9-_.]+$` or a URI, a chunk length
of 0, `consolidated_metadata: null`, and a structured v2 dtype with
`fill_value: 0`. Also refused: in a group's `consolidated_metadata`, a key that is
not a valid node path (`""`, `"/a"`, `"__a"`), a node below an array, and
a node whose parent group is missing.

The v2 validators now check `compressor` and each filter against the
numcodecs definition for its `id`, and check `fill_value` against `dtype`.
A gzip `level` of 99, an unknown blosc `cname`, a `delta` filter with no
`dtype`, or a `<f4` fill value of `"abc"` is now a problem. A codec `id`
that the scope does not define is not checked.

Problem kinds are more precise. An undeclared key in a closed object (a
v2 `.zgroup`, a `.zmetadata` envelope, `consolidated_metadata`, a field
envelope) is `unknown_key`, not `invalid_value`. A value of the wrong JSON
type is `invalid_type`, and a field without `name` is `missing_key`.
Messages name values in JSON terms. The pydantic field types raise one
error per problem, with the problem's kind as `type` and its `loc`,
`input` and `ctx`, instead of one `value_error`.

New public API besides the modules above: `NodeName` and `NodePath` (in
`zarr_metadata.v3`), and `validate_node_name_v3`, `is_node_name_v3`,
`parse_node_name_v3` and the `node_path` versions, which check node names
and paths; `repair_node_metadata_v3` and
`repair_consolidated_metadata_v2`, with `Repair` and `RepairKind`, which
apply the writer-bug repairs without reading the result;
`node_metadata_from_json_v3`, `node_metadata_from_key_value_v3` and
`validate_node_metadata_v3`, which read a `zarr.json` of either node type;
and `zarr_metadata.json_schema`, the home of the JSON Schema functions.

A model's field members (`data_type`, `chunk_grid`, `chunk_key_encoding`,
`codecs`, `storage_transformers`; a v2 `dtype`, `compressor` and
`filters`) are now the `AcceptedField` or `UnclaimedField` the read
produced, not JSON, so `model.dtype == "<f4"` is now False: compare
`field.json`, or use `model.to_json()`. Objects and arrays in the other
members are read-only mappings and tuples.

The pydantic field types read the scope from pydantic's validation
context: a `Context` itself, or a mapping that holds the v3 scope under
`CONTEXT_KEY` (`"zarr_metadata_context"`) and the v2 scope under
`CONTEXT_KEY_V2` (`"zarr_metadata_context_v2"`), both exported from
`zarr_metadata.pydantic`.
