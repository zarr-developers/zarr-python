`to_json`, `to_key_value` and `canonicalize` write every extension point
but a data type as an object -- `{"name": "crc32c"}` -- where they wrote
the bare name `"crc32c"` for a field with nothing to configure. A Zarr
v3.0 reader takes no short-hand name in `codecs`, and no zarr-python
release reads one there or in `chunk_key_encoding`, so a document the
package wrote could not be opened by them. A data type with nothing to
configure is still written by its bare name, as core data types are.
A field alone -- `ZarrV3NamedConfig.to_json`, and the pydantic
`ZarrV3MetadataField` -- keeps its shortest spelling, since which one its
readers take depends on the extension point it fills. `to_json` and
`to_key_value` write a configuration as it was read, so a field one holds
-- a shard's inner codecs -- keeps the spelling the document gave it;
`canonicalize` writes those as objects too.
